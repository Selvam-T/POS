POS Development Across Ubuntu & Windows VMs

Architecture, UI rendering, Python environments, dependencies, PyInstaller and Windows release testing.

Recommendation: Use the Ubuntu VM for primary development and the Windows 11 VM for frequent Windows UI validation, hardware integration testing and release builds. Use the same version-controlled source but keep a separate .venv in each operating system.

Windows should remain the authority on how the final POS interface actually behaves. Avoid leaving all Windows testing until the end.

1Development architecture

Your Windows-targeted POS can be developed on Linux. Since the school Linux host does not provide you with sudo privileges, your Ubuntu guest is a useful controlled development workspace. Reserve Windows 11 Enterprise VM for target-platform verification and creation of production executables.

School Linux hostQEMU/KVM, libvirt and virt-manager
↓ Guest VMs ↓
Ubuntu VMVS Code, Python, PyQt5, Qt Designer, Git
Windows 11 VMUI testing, hardware checks, PyInstaller builds
↕ Common source history ↕
GitHub repositorySource, UI files, assets, requirements and build instructions
Important adjustment: Test the Windows UI regularly, especially after changes to layouts, fonts, scaling or the customer display. Windows should not be used only for final testing.

Benefits

  • Ubuntu can hold the full developer toolset while Windows remains lean.
  • The same source history can be checked out on either guest.
  • Independent environments can be rebuilt reliably.
  • Final executable packaging happens on the target Windows platform.

3Why UI rendering can differ

Your MacBook and Windows VM rendering problems might arise from more than simple pixel differences. The exact root cause has not yet been established.

Potential causeTypical symptomInspect
DPI scalingClipped controls or inconsistent geometryWindows 100%, 125%, 150% scaling; Qt logical pixels
Hard-coded widget geometryOverlaps or squeezed panels.ui layouts, size policies, fixed widths and heights
QXL/SPICE guest displayResolution or monitor-sizing issuesVirtual graphics, virt-viewer, guest display settings
Font metrics/stylesText no longer fitsFonts, QSS, system style, font sizes
Different Qt/PyQt5 versionsSubtle visual differencesLibrary and Qt versions on both guests

Controlled diagnostic sequence

  1. Set Windows display scaling to 100%.
  2. Use a fixed resolution such as 1920 × 1080.
  3. Run POS directly with Python, before packaging it.
  4. Confirm installed Python, PyQt5 and Qt versions.
  5. Identify whether the defect is clipping, misplaced controls, font enlargement or unexpected window resizing.
  6. After establishing a good baseline, test 125% and 150% scaling and the second screen.
Your existing Windows VM: QXL/SPICE was configured for two-monitor support. Keep that known configuration initially to minimize moving parts. A lasting fix may require changes to .ui, .qss or Python layout logic, not the VM.

The source requires Python 3.12 or later because of its f-string syntax. Ubuntu currently uses 3.12.3; Windows was verified with 3.12.10. Record these patch-version differences when comparing behaviour. Python 3.13 is not the current documented baseline.

Ubuntu system prerequisites

sudo apt update
sudo apt install python3.12-venv libxcb-xinerama0

Assumes Python 3.12 is installed. python3.12-venv supplies environment creation support, including ensurepip. Ubuntu package libxcb-xinerama0 supplies libxcb-xinerama.so.0, required by the installed Qt XCB platform plugin to initialize the graphical interface. These are Ubuntu system packages, so keep them out of Python's requirements.txt.

Ubuntu: create a new environment

cd /home/sthiagar/Desktop/Projects/POS_Dev
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r Project/requirements.txt
python --version
python -c "import sys; print(sys.executable)"

cd Project

Adjust the checkout path if needed. The interpreter should be POS_Dev/.venv/bin/python. In VS Code, use Python: Select Interpreter and select that interpreter.

Ubuntu: Qt startup troubleshooting

On November 13, startup ended with Aborted (core dumped) and a log message saying no Qt platform plugin could be initialized. A dependency check identified libxcb-xinerama.so.0 => not found. Install libxcb-xinerama0, then retry. To inspect dependencies from the repository root:

ldd .venv/lib/python3.12/site-packages/PyQt5/Qt5/plugins/platforms/libqxcb.so

A successful pip check does not check Ubuntu system libraries. If the library is already installed, inspect the current error and other missing dependencies. The application log is live_logs/error.log; use entry timestamps, rather than the export time, to identify new failures.

6PyInstaller: Windows executable packaging

PyInstaller bundles Python applications for distribution. For your PyQt5 POS it can include the interpreter, imported Python modules and dependent libraries, allowing the customer PC to run the application without a separate Python installation.

PyInstaller does not convert the whole program into native compiled machine code. Files loaded dynamically (icons, QSS, .ui, data templates) may require explicit packaging rules and runtime path handling.

Install in Windows .venv

python -m pip install pyinstaller

Basic example

pyinstaller --onefile --windowed main.py

Creates a basic output structure such as:

Project/
├── main.py
├── build/
├── dist/
│   └── main.exe
└── main.spec
OptionResultWhen useful
--onefileOne .exeSimple distribution; bundled contents extracted when launched
--onedirDirectory with EXE and dependenciesEasier initial debugging and dependency inspection
--windowedHides console on WindowsGUI releases; keep a console-enabled debug build when diagnosing crashes
For POS: Start with --onedir. After confirming resources, database paths, peripherals and startup work, evaluate --onefile if needed.

PyInstaller builds Windows executables on Windows, not directly from a Linux build host.

7Lean Windows environment and release checks

Your Windows VM does not need a full development IDE. For packaging, keep Python, runtime dependencies, PyInstaller, Git or an exported source copy, PowerShell and minimal diagnostic tools.

Windows setupPurposeInstalled software
Build VMRun source, diagnose GUI, produce EXEPython, virtual environment, dependencies, PyInstaller and Git
Clean test VM or snapshotProve customer-like deploymentPackaged POS and required drivers, ideally no Python installation

Repeatable release workflow

  1. Complete programming and tests in Ubuntu.
  2. Commit the selected code and check out the same Git commit in Windows.
  3. Recreate or refresh the Windows .venv from pinned dependencies.
  4. Run POS directly in Windows and validate layout, DPI and transactions.
  5. Build the distributable using PyInstaller.
  6. Test the packaged application in a clean Windows environment, including assets, writable data, receipts and devices.

Use repeatable build commands or a .spec file once the packaging requirements are stable.

8POS-specific hardware and deployment concerns
  • USB HID scanners: Test keyboard-event flow and focus in Windows even if you mock scanner input in Ubuntu.
  • Epson receipt printer: Test Ethernet/ESC-POS output, 80 mm receipt formatting and connectivity in the customer-like Windows environment.
  • Cash drawer: Verify the printer-driven drawer command with real hardware.
  • Secondary customer monitor: Confirm multi-monitor display selection, extended desktop, full-screen UI and DPI behaviour.
  • SQLite persistence: Keep writable receipts, application data and logs outside read-only packaged resources.

Keep hardware support in separate modules with mocked substitutes for everyday Ubuntu testing. A working mock does not prove that physical hardware is accessible to a Windows guest; use appropriate pass-through or network access during integration tests.
